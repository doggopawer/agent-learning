# 평가와 승인 기록

## 세 영역의 통과 기준

| 영역 | 핵심 질문 | 통과에 필요한 관찰 |
| --- | --- | --- |
| technical | 왜 이 구조인가? 실패하거나 동시에 요청되면? | 사용자가 원리·대안의 차이·실패 조건을 자기 말로 설명 |
| business | 누구에게 어떤 업무가 허용되는가? | 주체·대상 회사·권한·상태·예외가 업무 결과와 연결됨 |
| code | 어느 파일과 메서드를 거치는가? | 실제 진입점 → 업무 처리 → 권한 → 저장·응답을 추적하고 변경 영향을 예측 |

암기한 이름을 나열하는 것만으로 통과시키지 않는다. 업무와 무관한 어려운 문제로 평가 범위를 확대하지 않는다. 약한 영역만 교육·재질문한다. 과거 통과 기록은 관련 코드와 범위가 같을 때 활용하고 기억이 흐릿하면 짧은 확인 질문을 한다.

실습 중심 세션에서는 구두 답변 외에도 학습자가 직접 추적한 값·작성한 코드·실험의 예상과 관찰·조건을 바꾼 과제 해결을 함께 근거로 삼는다. 원리와 관찰 결과를 연결해 설명해야 하며 테스트 성공만으로 통과시키지 않는다. 멘토의 시연, 골격 제공, 힌트, 사용자의 독립 해결을 구분한다. 이미 아는 기초 질문만 반복하지 않고 부족한 원리는 설명·예제로 가르친다.

학습용 실습은 세션에 기록하며 제품 구현 승인을 요구하지 않는다. 아래 gate 기록은 원본 제품의 구체적인 개발 전달 범위에 적용한다. 실습 과제 하나를 해결한 것이 전체 프로젝트의 세 영역을 통과했다는 뜻은 아니다.

각 영역 상태는 `pending`, `learning`, `passed` 중 하나다. `passed`에는 실제 사용자 답변과 그 답변이 기준을 충족한 이유가 필요하다. 긍정적인 반응만 있고 설명이 없으면 `pending` 또는 `learning`으로 둔다.

## 기록 형식

`records/gates/<project-id>/<task-id>.json`의 필드는 다음과 같다. 첫 학습의 미응답 예제 파일을 참고하되 사용자의 답변을 복제하지 않는다.

- `schema_version`: 2
- `task_id`: 학습 과제 식별자
- `scope`: `project_id`(등록 ID), `project_root`(확인한 원본 절대 경로), `goal`(구체적인 개발 대상), `allowed_paths`(원본 기준 상대 경로 배열), `exclusions`(제외 항목 배열)
- `sources`: 읽은 실제 파일의 `path`, `sha256` 배열
- `assessments`: `technical`, `business`, `code` 각각의 `status`, `question`, `answer`, `evidence`, `reason`
- `passed_at`: 전체 통과 시각. 시간대가 있는 ISO 8601 값. 미통과면 null
- `assessed_scope_sha256`: 통과 당시 scope의 지문. 미통과면 null
- `approval`: `status`(`pending` 또는 `approved`), `message`(사용자 승인 원문), `evidence`(대화 출처), `at`(시간대 포함), `scope_sha256`

순수 개념 학습은 기술 이해를 세션에 기록하고 적용할 업무·코드가 없으면 이유와 함께 `not-applicable`로 둔다. 이는 세 영역 통과나 개발 전달 자격이 아니다. 프로젝트가 달라지면 관련 업무·코드를 새로 확인한다.

지문에는 프로젝트 ID와 경로도 포함된다. 지문은 검증기 출력의 `current_scope_sha256`을 사용한다. 통과할 때만 `assessed_scope_sha256`을 채우고, 통과 이후 사용자가 그 범위를 승인했을 때만 approval을 채운다. 검증기는 값을 채우거나 상태를 올리지 않는다.

`scope`가 달라졌다고 옛 승인 지문을 새 값으로 자동 교체하지 않는다. 변경을 사용자에게 설명하고 필요한 재평가·승인을 받는다. 코드 해시도 새 파일을 읽고 평가에 미친 영향을 확인한 후 갱신한다.

`evidence`에는 대화 날짜·질문·해당 사용자 발언 등 확인 가능한 위치를 적는다. 실제 대화 식별자가 제공되지 않으면 만들어 내지 않는다. 검증용 합성 답변은 테스트에만 두고 실제 평가 파일에 옮기지 않는다.
