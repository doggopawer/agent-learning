# 광고주 회사 생성 — 첫 이해도 진단

[학습 홈](../../index.md) · [학습 진행 방법](../../learning-workflow.md)

학습 시스템 설치 후 기존 기능 학습을 시작했다. 기술·업무 시작 질문에 첫 답변을 받았고 보충 학습 중이다. 아래의 최초 준비 문항과 이후 실제 질문·답변을 구분한다. 제품 변경 요청·평가 통과·구현 승인은 없다.

## 먼저 답해 볼 질문

1. **기술:** 회사 저장과 생성자 담당 배정을 하나의 트랜잭션에서 처리하는 이유는 무엇일까? 배정 중 오류가 나면 어떤 결과를 기대하는가?
2. **비즈니스:** 광고주 회사를 생성하면 광고주 로그인 계정도 생성되는가? 이 동작을 누가 수행할 수 있고 어느 대행사에 속한 회사가 되는가?
3. **코드:** `ClientCompanyController.registerClientCompany`에서 시작해 권한 확인, 저장, 담당 배정까지 담당 파일과 메서드를 찾아 설명해 볼 수 있는가?

## 기존 기능 학습 시작 — 2026-11-16

사용자 요청: “기존에 마케스트림에서 만들었던 기능및 내용들을 학습하고 싶은데 어떻게 학습하는게 좋을까”. 제품 구현 요청이 아닌 기존 구현의 학습 요청이다.

멘토는 현재 기능 명세와 소스에서 광고주 생성, 로그인·권한, 등록·초대, 랜딩 편집, 게시, 문의·상담을 확인했다. [기능별 학습 순서](../../projects/markestream/learning-roadmap.md)를 제안하고 첫 주제를 광고주 회사 추가로 잡았다. 아직 순서에 대한 사용자 선호나 이해도 답변은 받지 않았다.

### 이번에 먼저 묻는 질문

1. **업무 이해:** 광고주 회사 추가가 끝나면 어떤 정보가 생겨야 한다고 생각하나요? 로그인 계정이나 운영 승인까지 생기는지도 예상해 보세요.
2. **기술 이해:** 저장 버튼을 누른 뒤 데이터가 DB에 남기까지 화면·서버·DB가 각각 무엇을 한다고 생각하나요? 낯선 단어가 있으면 그 부분부터 말해도 됩니다.

질문 제시 당시에는 두 질문 모두 미응답이었다. 첫 답변과 보충 학습은 아래에 이어 기록한다. 코드 읽기 진단은 답변 수준에 맞춰 짧은 실제 코드 조각으로 진행한다.

### 첫 코드 위치

화면의 `apps/admin-web/src/features/clients/useClientManagement.ts`에서 `submit()`을 읽고, `ClientCompanyController.registerClientCompany`와 `ClientCompanyService.registerClientCompany`로 이어갈 예정이다. 사용자가 직접 이 경로를 미리 찾아오거나 정답을 준비할 필요는 없다. 현재 파일 지문은 [학습 순서 노트](../../projects/markestream/learning-roadmap.md)에 기록했다.

학습 시작 시에는 질문 대기였고, 첫 답변 수신 후에는 **기본 흐름 학습 중·재질문 답변 대기**로 표시한다. 제품 테스트·빌드·서버 실행은 수행하지 않았다.


## 첫 답변과 보충 학습 — 2026-11-16

### 실제 사용자 답변

1. 업무 이해: “회사가 생기고, 로그인 계정이나 운영승인은 잘 모르겠다.”
2. 기술 이해: “화면에서 api를 호출하고, 서버가 받고 DB가 생성하는거 아닌가”

출처는 현재 학습 대화의 위 사용자 발언이다. 별도 대화 ID는 제공되지 않았다.

### 평가

- 업무: 회사 정보가 생긴다는 부분은 맞다. 로그인 계정과 운영 승인은 아직 구분하지 못한다고 명시했으므로 `learning`이다.
- 기술: 화면의 요청 → 서버 수신 → DB 저장이라는 큰 흐름은 잡았다. “DB가 생성”을 DB 자체를 새로 만든다는 오해로 단정하지 않는다. 회사 데이터 저장이라는 뜻으로 정리하고 서버의 입력·권한 확인과 업무 처리를 보충한다.
- 코드: 실제 코드에 대한 사용자 설명은 아직 없어 `pending`이다. 이름을 따라 읽는 것과 데이터 변경·실패 영향을 설명하는 것은 별도로 확인한다.

### 이번 설명

회사 정보, 로그인하는 사람의 계정, 회사의 운영 승인은 서로 구분한다. 회사 추가만으로 새 로그인 계정이나 운영 승인이 만들어지지 않는다. 생성자의 담당 관계를 연결하는 일은 계정 생성과 다르다.

[실제 생성 코드](../../projects/markestream/client-company-creation.md#이번에%20읽을%20두%20줄)의 `ClientCompany.register(...)`는 메모리의 회사 객체를 구성하고, `clients.saveAndFlush(client)`는 Repository를 통해 DB 저장을 요청한다. 둘째 줄을 실행했다는 것과 전체 트랜잭션 커밋 완료는 구분하며 상세 트랜잭션 학습은 이후에 이어간다.

[계층별 책임과 요청 흐름](../../concepts/layered-request-flow.md)에 서버의 규칙 확인·업무 처리와 객체 생성·DB 저장의 차이를 연결했다. 제품 코드는 수정·실행하지 않았다.

### 다음 확인 질문 — 답변 대기

1. 회사 이름만 등록한 상태에서, 새 담당자의 로그인 계정도 준비됐다고 볼 수 있을까요? 이유를 설명해 주세요.
2. 아래 코드에서 첫째 줄만 실행하고 둘째 줄을 실행하지 않으면, 서버 메모리와 DB에는 각각 무엇이 남을까요?

```java
ClientCompany client = ClientCompany.register(agencyCompanyId, name, clock.instant());
var saved = clients.saveAndFlush(client);
```

이 두 질문에 대한 사용자 답변은 아직 없다. 전체 이해도 통과·구현 승인도 없다. [학습 Canvas](../../maps/learning-map.canvas) · [전체 학습 순서](../../projects/markestream/learning-roadmap.md)


## 학습 방식 피드백과 대안 제안 — 2026-11-16

사용자 원문: “음... 내가 지금까지 같이 해봤는데 이게 기술적으로 얻는게 별로 없다고 느껴지거든...? 더 좋은 학습 방법 없을까”.

이는 앞의 확인 질문에 대한 답변이나 학습 중단 요청이 아니다. 단순 개념 확인 위주 진행에서 기술적인 학습 성과가 부족하다는 피드백이다. 이전 실제 답변과 미응답 문항을 보존하고 학습 방식을 다시 제안한다. 이해도 통과·구현 승인은 바꾸지 않는다.

멘토의 제안은 기술 목표를 하나 정하고, 실제 코드 추적 → 원리 설명과 시연 → 작은 학습용 구현 → 조건을 바꾼 실패 실험 → 도움을 줄인 재구현으로 진행하는 것이다. 질문은 다음 작업에 필요한 부분을 파악하는 데 사용하고, 같은 개념의 단순 확인을 반복하지 않는다.

예시 목표: 회사 생성 API의 요청이 서버 메서드로 전달되는 과정을 이해하고, 작은 학습용 API에서 이름 검증과 저장 호출을 직접 작성·확인한다. 멘토는 처음에 골격과 예제를 제공하고 학습자가 핵심 부분을 작성한 뒤 힌트만으로 변형 문제를 해결하도록 제안한다. 원본 프로젝트와 분리된 학습용 복사본을 사용할 수 있으나, 아직 실습 코드를 생성하거나 실행하지 않았다.

실습의 진행 기준은 사용자가 직접 추적한 값·작성한 코드·관찰한 결과·변형 문제 해결이다. 예측과 관찰이 다른 이유를 설명한 뒤 노트·Canvas에는 그 결과를 남긴다. 사용자가 이 대안을 선택·실행한 것으로 기록하지 않는다.

참고한 프로그래밍 교육 구성: [PRIMM 원문](https://kclpure.kcl.ac.uk/ws/portalfiles/portal/79583213/version_pure_primm_1.pdf)의 예측·실행·분석·수정·직접 제작. 연구는 학교 프로그래밍 교육의 맥락이며 이 프로젝트의 성인 학습 효과를 직접 검증한 자료는 아니다. 위 내용은 현재 피드백에 맞춘 멘토의 적용 제안이다.


## 학습 방식 정정 — 서로 질문하고 내 말로 정리하기

사용자 설명: “실습은 잘 모르겠거든...?” 및 “나는 이런식으로 서로 질문하고 그다음에 그걸 이제 정리하고 싶은거거든 내가 이해했던 것들을 내 언어로 정리하는 과정”.

[사용자가 공유한 참고 대화](https://chatgpt.com/share/6afa84d8-6830-83ec-b432-2ea8ce90d690)를 읽었다. 공유된 부분은 개념의 필요성·동작 흐름·헷갈렸던 점·프로젝트 적용을 구분해 기술 위키로 남기는 방법을 설명한다. 사용자는 이를 서로 질문하며 이해하고 자기 언어로 정리하는 흐름으로 원한다고 명확히 했다.

멘토가 기술적 깊이를 실습 선호로 잘못 해석했다. 기본 지침을 궁금한 점 → 원리·흐름 설명 → 서로 후속 질문 → 사용자의 자기 설명 → 보충·교정 → Obsidian·Canvas 연결로 수정했다. 실습·코드 작성·실행은 사용자가 원할 때만 선택한다.

정리할 때는 사용자가 말한 원문을 먼저 보존하고, 그 의미를 유지해 다듬은 표현과 멘토의 추가 설명·오류 교정을 구분한다. 사용자가 아직 정리하지 않은 내용을 멘토가 1인칭 자기 설명으로 대신 작성하지 않는다. 한 주제가 정리될 때 진행하며 매 대화 뒤 정답 시험·요약을 강요하지 않는다.

이번 발언은 학습 방식에 대한 선호이며 앞서 제시한 회사 생성·DB 저장 확인 질문의 답변이 아니다. 기존 실제 답변·평가 상태·제품 구현 승인 상태는 그대로 유지한다.
