# 회사 등록·검증·초대

구현 계약 v0.5 · 2026-11-13. [ADR-006](../adr/006-company-registration.md), [V4](file:///Users/dhkim/Desktop/ml-project/markestream/database/migrations/V4__company_registration_and_invitations.sql), [API 계약](file:///Users/dhkim/Desktop/ml-project/markestream/contracts/openapi.yaml)을 함께 따른다.

## 이용 흐름과 화면

대행사 이용자는 이메일을 인증한 계정으로 로그인한다. 소속이 없으면 **대행사 등록**과 **받은 초대**를 선택한다. 대행사를 만든 계정은 기본 팀장 그룹에 연결되지만, 회사가 승인되기 전에는 회사 등록 신청만 진행할 수 있다.

1. **대행사 설정 → 회사 정보**에서 상호·사업자등록번호·대표자·개업일·연락 담당자·이메일·전화번호를 저장한다. 웹사이트는 선택이다.
2. 사업자등록증을 비공개 첨부한 뒤 신청한다. 국세청 진위확인 결과와 영업 상태를 저장한다.
3. **시스템 → 회사 심사**에서 운영자가 신청자의 등록 권한을 독립적으로 확인하고, 확인 방법·내부 근거·신청자에게 전달할 처리 사유를 기록한다. 자동 조회 성공만으로 승인되지 않는다.
4. 승인 후 직원 이메일 초대와 광고주 회사 등록을 사용할 수 있다. 초대 대상은 회사 검색이나 ID 입력 없이 이메일과 권한그룹으로 정한다.
5. 광고주 회사는 대행사가 표시 이름으로 먼저 만든다. 해당 회사의 **랜딩·문의·구성원·회사 정보** 탭에서 업무를 진행한다. 담당자 탭은 대행사 담당 직원과 광고주 측 이용자를 구분한다.
6. 광고주 회사의 사업자 정보와 대행 관계를 별도로 심사한다. 승인 전에도 담당자 배정과 랜딩 초안 작성은 가능하다. 광고주 계정 초대·랜딩 게시·공개 문의 수집은 대행사와 광고주 회사가 모두 승인되고 활성 상태여야 한다.

직원은 **대행사 설정 → 팀원**, 회사별 계정은 **광고주 회사 → 담당자**에서 초대한다. 회사 검색 가입 신청과 가입 승인 요청함은 MVP에 넣지 않는다. 시스템 계정 등록은 기존 운영자 절차를 유지하며 공개 회원가입으로 시스템 권한을 얻을 수 없다.

## 회사 참여 전 화면과 업무 화면

회원가입 후 회사 소속이 없으면 로그인과 같은 전용 온보딩 틀로 시작한다. 데스크톱은 Granter의 구성처럼 왼쪽 서비스 소개와 오른쪽 양식으로 나누고, 모바일에서는 양식만 표시한다. 가입 진입은 이메일을 먼저 받고 인증 서버로 전달한다. 회사 참여 전 첫 화면에서 받은 초대를 바로 조회하며, 대행사 계정은 초대가 없으면 새 대행사 생성으로, 광고주 계정은 초대 대기와 다시 확인으로 안내한다. 대행사 이름 등록·회사 정보 작성·서류 제출·승인 대기도 같은 온보딩 틀을 사용한다. 이 단계에는 업무용 사이드바·대시보드 메뉴가 없다.

초대 링크는 기존 소속 유무와 관계없이 같은 온보딩 틀에서 회사·권한그룹을 확인하고 명시적으로 수락한다. 수락 성공 후 추가 확인 버튼 없이 새로 참여한 회사로 이동한다. 광고주 계정은 해당 회사의 실제 권한을 조회해 문의·랜딩·구성원·회사 정보 순으로 접근 가능한 화면으로 이동하며, 조회·이동 실패 시 참여 완료 상태에서 재시도한다. 다른 등록 중인 회사가 있어도 새로 수락한 회사로 이동한다. 이미 참여한 회사의 일반 받은 초대 목록과 시스템 운영 화면은 업무용 틀을 유지한다. 소속 확인 중·오류·빈 목록·사용할 수 없는 초대도 같은 참여 전 틀에서 안내한다.

대행사 승인 대기 화면의 상태 다시 확인은 회사 신청과 소속 정보를 함께 갱신한다. 승인 완료 후에는 업무용 틀을 사용한다. 프론트는 기존 업무 훅을 유지하고 desktop/mobile 페이지에서 공통 AccessShell을 조립한다.

## 무엇을 검증하는가

| 구분 | 확인 내용 | 한계 |
| --- | --- | --- |
| 이메일 인증 | 로그인한 사람이 해당 메일을 받을 수 있는지 | 회사 대표·직원이라는 증명은 아님 |
| 국세청 조회 | 번호·대표자·개업일·상호의 일치와 계속/휴업/폐업 상태 | 신청자의 회사 등록 권한이나 대행 계약은 증명하지 않음 |
| 대행사 수동 확인 | 공식 연락처 확인 또는 위임 자료에 근거한 등록 권한 | 운영자가 실제 확인 후 근거를 남겨야 함 |
| 광고주 수동 확인 | 대행 계약·위임 증빙 또는 광고주 공식 연락처 확인 | 사업자번호 일치만으로 관계 승인 불가 |

필수 정보는 사업자등록증의 표기를 기준으로 입력한다. 광고주 신청의 서류 첨부는 선택이며, 관계 확인 근거는 시스템 심사에서 필수다. 대행사 신청에는 사업자등록증이 필수다. 조회 결과가 불일치하면 입력값·개업일·대표자 표기 등을 확인하고 보완한다. 조회 장애나 키 미설정은 가짜 회사라는 뜻이 아니며 **확인 대기**로 남는다.

## 신청 상태와 승인 정보

| 상태 | 가능한 다음 동작 |
| --- | --- |
| DRAFT | 정보·첨부 수정, 신청, 철회 |
| SUBMITTED | 사업자 재확인, 운영자 심사, 신청자 철회. 정보·첨부 변경 불가 |
| NEEDS_INFO | 사유 확인 후 정보·첨부 보완, 재신청, 철회 |
| APPROVED | 승인 스냅샷 보존. 정보 변경은 새 신청 |
| REJECTED / WITHDRAWN | 기존 기록 보존 후 새 신청 |

사업자 결과는 UNCHECKED / MATCHED / MISMATCH / UNAVAILABLE, 영업 상태는 UNKNOWN / ACTIVE / SUSPENDED / CLOSED다. **MATCHED + ACTIVE**와 수동 확인 근거가 모두 있어야 승인한다. 관리자도 미확인·불일치를 수동으로 일치 처리할 수 없다. 재확인은 제출 상태에서 명시적으로 실행하며, 주기적 휴·폐업 감시는 이번 범위가 아니다.

제출한 사업자 정보는 심사 스냅샷이다. 승인할 때만 회사의 공식 정보를 갱신한다. 승인된 회사가 변경 신청을 하더라도 기존 승인 정보는 새 신청 승인 전까지 유지된다. 버전이 달라졌거나 철회된 신청에 늦게 도착한 외부 조회 결과는 적용하지 않는다. 회사 승인과 기존 시스템의 이용 중지(disabled_at)는 별개이며, 중지된 회사는 게시·접수를 사용할 수 없다.

## 데이터와 파일

- 기존 계정 테이블에 서명된 로그인 정보의 이름·이메일·인증 시각을 기록한다. 비밀번호는 인증 서버에만 있다.
- 회사 테이블에 공식 사업자 정보와 approved_review_id를 추가한다. 기존 회사 ID와 업무 데이터는 유지하고, 기존 회사를 자동 승인하지 않는다.
- company_reviews에 상태·버전·제출 정보·자동 결과·수동 근거·처리 사유를 기록한다. 회사마다 진행 중 신청은 하나다. 승인 참조는 해당 회사의 신청으로 제한된다.
- company_documents는 신청별 비공개 객체의 메타데이터다. PDF/PNG/JPEG만, 파일당 10MB·신청당 10개까지다. 확장자 대신 파일 시그니처를 검사한다. 다운로드는 현재 회사 권한을 검사하고 첨부파일로 반환하며 캐시하지 않는다.
- 파일 본문은 공개 HTML 저장소와 분리된 MARKESTREAM_DOCUMENTS_ROOT에 둔다. 백업·접근 제한을 별도로 구성해야 한다. 문서 삭제는 초안/보완 상태에서 논리 삭제하며, 종료 신청과 파일의 보관 기간·영구 삭제 자동화는 후속 운영 정책이다.
- account_invitations에 회사·계정 종류·이메일·그룹·초대한 사람·만료·수락·회수 상태와 SMTP 전달 상태를 둔다. 원문 초대 토큰은 저장하지 않는다.
- audit_logs, membership_requests, permission_group_workspaces는 추가하지 않는다.

## 초대와 메일 전달

초대는 7일간 유효하며 한 번만 수락한다. 초대 이메일과 **현재 서명된 인증 이메일**, 계정 종류가 같아야 한다. 링크로 진입한 뒤 회원가입·이메일 인증을 완료해도 원래 초대 화면으로 돌아온다. 이미 로그인한 수신자는 받은 초대 목록에서도 수락한다. 수락 즉시 회사 소속과 그룹을 부여하며 관리자 재승인은 없다.

같은 회사·종류·이메일의 재초대는 1분 뒤 가능하고 이전 링크를 회수한다. 초대한 사람의 현재 권한·회사 승인·그룹 위임 범위를 수락 시점에 다시 검사한다. 취소·만료·권한 회수된 초대는 수락할 수 없다. 수락 요청 재전송은 같은 결과를 반환하되 이미 회수한 소속을 다시 활성화하지 않는다.

DB에서 메일 작업을 선점한 후 DB 잠금 밖에서 SMTP를 호출한다. 임대·세대 검사와 최대 5회 재시도를 사용한다. SMTP 타임아웃 뒤 같은 초대 메일이 중복 도착할 수 있지만 링크는 같은 단일 수락 규칙을 따른다. 전달 실패는 목록에 표시하며 재초대할 수 있다. 메일 전달 성공은 가입 완료와 다르다.

토큰은 난수 nonce와 서버 비밀키의 HMAC으로 만들고 조회용 해시를 저장한다. 비밀키를 교체하면 대기 중 링크가 무효가 되므로 취소 후 재초대한다. 외부 공개 원점은 HTTPS를 사용한다(로컬 localhost/127.0.0.1 개발 HTTP만 허용).

## 권한과 이전 설치

| 코드 | 영역·대상 |
| --- | --- |
| company.registration.read / manage | 대행사 회사 신청 조회/관리, 대행사·시스템 계정 |
| client.registration.read / manage | 광고주 회사 신청 조회/관리, 대행사·광고주·시스템 계정 |
| system.company.review | 전체 회사 심사, 시스템 계정만 |
| member.manage / client_user.manage | 각각 직원/광고주 이용자 초대 및 관리 |

기존 그룹에는 새 권한을 자동으로 넣지 않는다. 업그레이드 후 기존 운영자가 **시스템 그룹**에서 심사 권한을, 대행사 권한그룹에서 회사 등록 조회·관리 권한을 명시적으로 배정해야 한다. 신규 대행사의 팀장 템플릿에는 신규 등록 권한이 포함되고 마케터에는 광고주 등록 조회 권한만 포함된다. 신규 기본 광고주 그룹은 상담 권한을 포함한다([권한 명세](07-permissions.md)). 기존 그룹은 자동 변경하지 않는다. 권한 이름이 아닌 코드와 범위로 판정한다.

## 로컬 설정과 재현

`npm run local:up -- demo|work|qa`는 저장소 루트의 `.env.local`을 읽는다. 다른 파일은 `ADDOCK_ENV_FILE`로 지정한다. [.env.example](file:///Users/dhkim/Desktop/ml-project/markestream/.env.example)을 참고하되 채운 환경 파일은 커밋하지 않는다. 기존 개별 실행 명령은 shell export가 필요하다.

- MARKESTREAM_BUSINESS_API_KEY: 공공데이터포털 Decoding 서비스 키. 없으면 네트워크 호출 없이 UNAVAILABLE로 처리한다.
- MARKESTREAM_SMTP_HOST/PORT/USERNAME/PASSWORD/AUTH/STARTTLS, MARKESTREAM_MAIL_FROM: 실제 SMTP 설정. 기본값은 로컬 Mailpit(1025)이다.
- MARKESTREAM_INVITATION_SECRET: 배포 시 독립 생성한 32바이트 이상 비밀값으로 교체한다. 개발 기본값을 운영에 사용하지 않는다.
- MARKESTREAM_PUBLIC_ORIGIN: 이메일에서 열 프론트 원점. 실제 배포에서는 HTTPS로 설정한다.
- MARKESTREAM_DOCUMENTS_ROOT: 비공개 파일 절대 경로 권장.

`npm run infra:up` 후 [앱](http://127.0.0.1:5173/)과 [로컬 메일함](http://127.0.0.1:8025/)을 연다. Mailpit은 외부 수신함으로 전달하지 않는다. Keycloak Realm의 회원가입·이메일 인증·SMTP도 필요하다. 신규 볼륨은 import 파일에 포함되어 있고, **기존 볼륨은 자동 갱신되지 않아** 별도로 해당 Realm 설정을 업데이트해야 한다. 컨테이너 안 Keycloak의 SMTP 호스트는 mailpit이고 호스트에서 실행하는 API는 127.0.0.1이다.

## 실제 확인한 Granter 화면을 적용한 가입·온보딩 (2026-11-12)

실제 관찰 범위는 이메일 인증번호, 이름·휴대폰 인증·비밀번호·동의 화면, 회사 정보 폼과 마지막 회원가입 버튼까지다. Granter의 회사 등록 완료·가입 후 첫 화면·내부 사업자 검증 정책은 확인하지 못했다. 이 구간을 보았다고 기록하거나 추정해 업무 대시보드를 바꾸지 않는다.

현재 AdDock 가입은 인증 서버의 이메일 인증번호 → 이름 하나·휴대폰 코드·비밀번호·이용 안내 → 회사 정보 또는 받은 초대로 이어진다. 신규 가입의 이메일은 계정 생성 전에 확인한다. [인증 확장](file:///Users/dhkim/Desktop/ml-project/markestream/auth/keycloak-provider)에서 서버 인증 세션·주소/번호에 묶인 6자리 코드를 검증하며 비밀번호·프로필 검증과 사용자 생성은 Keycloak 부모 구현을 사용한다. verifyEmail 정책은 유지하고 기존 사용자의 인증 상태·비밀번호·필수 동작은 변경하지 않는다.

이메일 진입·코드 대기는 소개 패널과 양식으로 나누고, 인증 이후에는 흰 배경 중앙 폼과 상단 진행 표시로 전환한다. 모바일은 별도 페이지를 조립하며 같은 훅의 초안을 유지한다. 업무 화면의 UI Kit·제품 색과 기존 보더 색 포커스를 유지한다. 가입 화면에만 테두리 입력을 사용한다.

휴대폰은 개발용 로컬 문자함이다. ADDOCK_LOCAL_SMS=true, loopback 인증 URL, 로컬 SMTP 조건이 모두 맞아야 발송·검증할 수 있으며 실제 문자나 휴대폰 소유 증명을 제공하지 않는다. `휴대폰번호@sms.addock.local` 앞으로 보낸 테스트 문자는 Mailpit에서 확인한다. 코드는 5분 만료, 재발송 60초 간격, 대상당 15분에 5회 발송, 코드당 5회 검증 제한과 단일 소비를 적용한다. 휴대폰 API는 동일 출처·인증 세션 쿠키·client/tab·서버 nonce·이메일 확인을 검사한다. 미설정 운영 환경을 인증 성공으로 대체하지 않는다.

소속·초대가 없는 계정은 중간 가입 완료·환영 안내 없이 회사 정보 양식을 연다. 이름만 먼저 만드는 단계를 합쳐 POST /agency-companies/onboarding으로 회사·기본 그룹·첫 팀장 소속·등록 초안을 한 트랜잭션에 저장하고 서류 단계로 이어간다. 입력 오류나 저장 실패로 빈 회사가 남지 않는다. 이 API는 심사 제출·자동 사업자 조회·운영 승인을 수행하지 않는다. AdDock에 필요한 상호·사업자번호·대표자·개업일·업무 연락 정보를 사용하며, 저장 기능이 없는 Granter의 이미지·설문·기능 카드를 복제해 표시하지 않는다.

## 공통 로그인과 회사 자동 연결 (2026-11-12)

대행사/광고주 선택을 제거하고 공통 로그인·회원가입을 사용한다. 인증 후 GET /me/session으로 본인의 회사·초대를 확인한다. 소속이 하나면 연결하고, 여러 회사나 여러 초대가 있으면 회사 이름을 선택한다. 한 개의 초대만 있다면 해당 초대의 확인 화면으로 이동하며, 명시적인 수락 전에는 소속·그룹을 부여하지 않는다. 새 계정이고 소속·초대가 없으면 대행사 생성 안내를 제공한다. 초대 링크의 종류 쿼리와 브라우저 저장값을 권한 근거로 사용하지 않는다.

광고주는 해당 회사의 허용된 기능으로 진입한다. 승인 대기 중에도 등록 조회·관리 권한이 있으면 회사 등록 상태 화면으로 진입하고, 그 권한이 없으면 회사 확인 대기와 담당자 문의를 안내한다. 여러 소속에 다른 계정 종류가 섞여 있어도 회사 이름으로 전환하고 내부 인증 클라이언트만 SSO로 변경한다. 새 초대 메일은 공통 /#/invitations/{token} 링크를 사용하며 이전 ?account=... 링크도 초대 자체를 검증해 처리한다.

검증: Admin API 전체 build와 84개 테스트를 통과했다. 신규 통합 테스트는 다른 계정 종류의 본인 소속 조회, 같은 이메일·다른 subject의 소속 격리, 두 종류의 초대 탐색과 무승격, 회수·비활성 소속 제외, 미인증·시스템 진입 차단, 무권한 소속의 업무 데이터 차단을 확인한다. 브라우저에서는 공통 로그인·모바일 가입, 광고주 소속 자동 연결, 여러 회사 선택, 초대 복귀·수락·자동 진입, 직원↔광고주 회사 SSO 전환, 기존 시스템 운영 진입을 확인했다. 테스트 소속은 로컬 합성 회사에서 생성·회수했으며 실제 회사 승인을 변경하지 않았다.

가입 화면 전환 검증(2026-11-12): Admin API 86개와 인증 확장 6개 테스트, 프론트 빌드를 통과했다. PC·390px 모바일에서 실제 이메일 코드·로컬 SMS 코드 발급/검증, 잘못된 코드·확인 생략·동의 누락·비밀번호 불일치의 계정 생성 차단, 회사 정보의 저장 실패/재시도·서류 단계 연결과 화면 전환 시 초안 유지를 확인했다. 기존 계정의 한 화면 로그인과 초대 링크의 신규 가입 → 원래 초대 복귀 → 명시적 수락 → 회사 진입을 검증하고 테스트 소속을 회수했다. 새 볼륨의 Realm import는 관리자 재설정 없이 이메일 코드와 단일 이름 폼까지 확인했으며 시스템 클라이언트의 직접 등록 요청은 403으로 거절했다. 이 결과는 Granter의 가입 완료 화면을 확인했다는 의미가 아니다.

회사 개업일은 `Asia/Seoul`의 업무 날짜와 비교한다. 저장·응답 시각은 기존 UTC `Instant`를 유지한다. 한국 시간 새벽에도 당일 개업일은 허용하고 다음 날짜는 신청할 수 없다. 직원·광고주 소속의 신규 생성과 회수 후 재가입은 초대 수락에서만 수행하며 기존 소속 변경 API와 그 호환 경로로 수락을 우회할 수 없다.


## 심사 대기와 문의 안내 (2026-11-13)

자동 확인 실패를 단순 “대기”나 “갱신 완료”로 표현하지 않는다. ## 회사 등록 문의 대화 (V11, 2026-11-13)

회사 정보와 시스템 심사 상세에 같은 신청의 ‘등록 문의’ 대화를 제공한다. 신청자는 `company.registration.read` 또는 해당 회사의 `client.registration.read` 범위에서 읽고, 작성에는 대응하는 manage 권한과 인증 이메일이 필요하다. 시스템 답변은 `system.company.review`를 요구한다. 심사자의 내부 확인 근거는 대화와 별개이며 신청자에게 노출하지 않는다.

`company_review_messages`는 신청·대행사 복합 FK, 정확히 한 종류의 작성자 FK, 이름·본문·서버 시각을 저장한다. 본문은 Unicode 1~2,000자다. 신청별 UUID `requestKey`의 같은 작성자·본문 재시도는 한 메시지로 처리하고 다른 본문의 키 재사용은 400으로 거절한다. 목록은 최신순 25건이며 `before`로 이전 대화를 조회한다. 보이는 탭에서 30초마다 갱신한다. 작성 전 초안은 계정·신청별 탭 저장소에 보관하고 로그아웃 시 제거한다. 별도 외부 알림이나 이메일 답변 통지는 아직 제공하지 않는다.

이름만 추가한 광고주 회사는 등록 준비 상태다. ‘표시 이름 수정’은 사업자등록증 상호나 승인 정보를 바꾸지 않는다. 조회만 가능한 계정에는 정보·상태 조회를 안내하고 사업자 재확인 버튼을 표시하지 않는다. 기존 사용자의 회사 전환에는 신규 가입 진행 표시를 붙이지 않는다.

국세청 키는 로컬 환경에 연결됐으며 실제 API 인증·불일치 처리까지 확인했다. 실제 회사의 일치 조회·수동 운영 승인은 아직 수행하지 않았다. 로컬 예시 회사의 합성 승인 fixture는 분리된 `addock_demo`에만 들어가며 제품 코드나 마이그레이션에서 실제 회사를 승인하지 않는다.

## 국세청 실제 연결 확인 (2026-11-13)

공공데이터포털의 국세청 개발계정 승인과 인증키 발급을 직접 확인했다. 키는 커밋 대상에서 제외되는 루트 `.env.local`에 저장하고 파일 권한을 600으로 제한했다. 키 원문·인증 쿼리 URL은 로그나 문서에 기록하지 않는다. 로컬 서비스를 재시작해 실제 설정을 반영했다.

실제 `/validate`는 HTTP 200, `status_code=OK`를 반환했고 합성 번호 `0000000000`은 `valid=02`로 불일치 처리됐다. 분리된 데모 회사의 새 변경 신청에서도 Admin API가 실제 국세청을 호출해 `MISMATCH` / `UNKNOWN` / `reason=NONE`을 저장하고 화면에 정보 불일치를 안내했다. 검증 신청은 철회했으며 기존 승인 참조는 유지됐다. 이 검증은 실제 회사의 정보 일치나 회사 운영 승인을 의미하지 않는다. 정상 일치 후 수동 승인·게시 조건은 기존 MySQL 통합 테스트에서 합성 공급자 응답으로 검증한다. 실제 회사 신청은 정확한 사업자 정보와 독립적인 등록 권한·대행 관계 확인이 필요하다.
