# MVP 구현 및 검증 현황

확인일: 2026-11-13. 계정·권한그룹 및 회사 등록·검증·이메일 초대를 포함한 현행 구현 기준이다. 로컬에서 실행·검증했고 원격 배포나 실제 고객 파일럿은 수행하지 않았다.

업무 페이지는 데스크톱·모바일을 별도 구성하고 같은 업무 훅을 주입한다. 공개되지 않은 랜딩에는 활성 주소를 표시하지 않는다. 목록과 요약에 예시 수치를 사용하지 않는다. UI Kit·대시보드 고정 이미지와 조작 가능한 미리보기는 기존 경로에 보존했다.

## 계정·권한그룹 추가 구현

- 회사와 계정을 분리하고 `agency_users`·`client_users`·`admin_users`를 별도 관리한다.
- 통합 권한그룹과 분류별 세부 권한 선택, 직원·광고주 탭, 기본 팀장·마케터·광고주 그룹, 회사 소속·담당자 배정을 구현했다.
- 시스템 계정은 모든 대행사 범위에서 그룹에 허용된 업무를 수행한다. 시스템 그룹·계정·권한 대상 정책과 대행사 이용 상태를 관리한다.
- 신규 기능 권한은 자동 부여하지 않는다. 명시적인 부여 권한과 위임 범위, 마지막 관리자 보호, 동시 편집 버전을 검사한다.
- `audit_logs`와 시스템 지정 대행사 테이블은 추가하지 않았다. 상세는 [권한 명세](07-permissions.md)를 따른다.

## 실행 검증

- Java 21.0.8, MySQL 8.4.11, 개발용 Keycloak, Vite의 로컬 주소에서 확인했다.
- 백엔드 111개 테스트 통과: Admin API 106개(권한·마이그레이션·등록·실제 SMTP·서비스 연결·문의 상담 협업 포함), 공유 문서·렌더링·파일 안전성 5개. 실패·오류 0개. 공개 문의폼 JavaScript 테스트 8개도 통과했다.
- 네 모듈의 Gradle `build`와 Spotless 검사 통과. Inquiry·Worker 동작은 Admin의 실제 서비스 연결 통합 테스트에서 검증한다.
- `npm run build`의 TypeScript 검사와 Vite 제품 빌드 통과.
- 1440×1000 데스크톱과 390×844 모바일에서 정상 화면, 빈 목록·필터 결과, 연결 실패·재시도를 확인했다. 모바일 편집 검증 실패에서 입력을 유지하고 저장 후 게시까지 수행했다.
- 공개 폼에서 합성 테스트 데이터를 접수하고 관리자 상세에서 같은 응답과 상담 이력을 확인했다. 테스트용 `MVP 데모 대행사 → 봄빛 스튜디오 → 브랜드 성장 상담`을 로컬에 남겼다.

- V1·V2 기존 DB에 V3를 실제 적용했고 기존 회사·계정·랜딩·게시·문의·상태 이력의 ID와 행 수를 보존했다. 적용 전 백업은 무시된 `.local/backups`에 보관한다.
- 권한 화면은 1280×900 데스크톱·390×844 모바일에서 확인했다. 실제 OIDC 로그인, 새 대행사 기본 그룹 생성, 사용자 정의 그룹 저장, 광고주 계정 연결, 담당자 자동 배정, 입력 오류 유지, 기기 전환 중 편집 초안 유지와 일부 선택 표시를 확인했다. 광고주 읽기 전용 화면에서 생성·수정 기능이 숨겨지고 연결된 회사만 표시되는지, 시스템 계정에서 모든 대행사와 정책·그룹·계정 화면이 열리는지 확인했다. 마지막 시스템 관리자 비활성화는 409로 거절되고 대화상자 내부에 오류가 표시된다. 검증용 `권한 검증 대행사 → 권한 검증 광고주` 합성 데이터를 추가했다.

## 후속 범위

실제 고객 파일럿 전에는 수집 항목·동의 문구·보관 및 삭제 절차를 정해야 한다. 원격 배포 시 내부 서명키·서비스 계정 연계, TLS·네트워크 경계, 서비스별 DB 계정, HTML 저장소, 공개 원점과 프록시 라우팅을 구성해야 한다. 로컬 구현과 운영 구성의 차이는 [ADR-004](../adr/004-mvp-runtime.md)에 기록했다.

방문 분석·광고 플랫폼 연동·커스텀 도메인·A/B 테스트·자동 보고서·결제는 [PRD의 다음 출시 범위](01-prd.md)다.

## 회사 등록·검증·초대 추가 검증 (2026-11-12)

- 등록 통합 15개와 MVP 통합 11개를 포함한 Admin 79개, 공유 문서 5개가 통과했다. 누락·불일치·미설정 NTS 응답은 승인되지 않으며, 수동 확인 근거·회사 격리·신청 버전·비공개 문서·동시 초대 수락·메일 인증/타입·취소·재발송·권한 회수·실제 Mailpit SMTP를 검증했다.
- 승인 해제 후 게시 요청·공개 페이지·접수를 차단하고, 이미 대기 중인 Worker 작업이 활성 버전을 교체하지 못하는 것을 실제 세 서비스 연결로 확인했다.
- 백업 후 기존 로컬 V1~V3 DB에 V4를 적용하고 기존 회사·랜딩·게시·문의의 ID 목록이 동일함을 확인했다. 기존 회사는 미승인으로 유지한다. 로컬의 기존 운영자/팀장 그룹은 개발 설정 과정에서 신규 등록·심사 권한을 명시 배정했다(마이그레이션의 자동 부여 아님).
- 390×844 모바일과 기본 데스크톱에서 회사 정보 작성·기기 전환 초안 유지·필수 입력 오류·비공개 PDF 업로드/다운로드·신청 대기·시스템 보완 처리를 확인했다. 실제 NTS 키는 없으므로 UNAVAILABLE이고, 실제 회사 승인 검증은 미수행이다.
- Keycloak 기존 볼륨의 회원가입·이메일 인증·로컬 SMTP를 갱신했다. 외부 SMTP 계정은 없으므로 Mailpit 안에서만 메일을 확인한다. 초대 이후 동작을 위한 별도 ‘로컬 QA · 초대 테스트 전용’ 합성 승인 fixture는 실제 사업자 검증이 아니다.

자세한 흐름·권한·설정과 제한은 [회사 등록·검증·초대](08-registration.md)를 따른다.

- 실제 브라우저에서 초대 메일 링크 → 개발 계정 로그인 → 초대 수락 → 회사 진입 → 담당 직원 배정을 완료했다. 수락 후 회사 목록 갱신과 담당 회사 없는 마케터의 빈 회사/문의 목록도 확인했다. 신규 가입은 실제 인증 메일 수신·인증 후 비밀번호 설정 단계까지 확인했으며, 해당 합성 계정의 비밀번호 설정 완료는 검증하지 않았다. 구성원 페이지의 모바일 가로 너비는 390px로 뷰포트를 넘지 않았다. 검증 스크린샷은 무시된 `.local/qa/registration-*.jpg`에 보관했다.

## 회사 참여 전 화면 분리 (2026-11-12)

소속 없는 계정의 시작·초대 수락과 대행사 등록·심사 대기를 중앙 카드 온보딩으로 분리했다. PC·390px 모바일에서 사이드바가 없는 것을 확인했다. 이름 입력 오류와 기기 전환 시 초안 보존, 실제 회사 등록 후 대기 화면, 초대 수락 후 해당 회사의 업무 틀 진입을 확인했다. 기존 등록 중인 회사가 있어도 새로 수락한 회사가 선택된다. 광고주 계정은 대행사 등록 동작 없이 초대 참여를 안내하며, 빈 목록·사용 불가 링크를 같은 틀에서 표시한다. 시스템 계정은 운영 틀로 진입하는 것을 확인했다. 합성 ‘로컬 QA · 온보딩 검증’ 대행사를 미승인으로 추가했다.

## 문의 상담 협업 추가 (2026-11-12)

문의별 상담 담당자는 해당 광고주 회사에 소속된 활성 광고주 직원만 선택한다. 대행사 직원의 담당 회사 배정과 구분하며 조회·처리 권한을 가진 직원만 후보로 제공한다. 담당자 변경·해제, 내 담당/미배정·재배정 필요 필터, 상담 메모 조회·작성·페이지와 작성자 이름·시각을 추가했다. UI는 기존 공통 컴포넌트를 조립하고 기기별 페이지 위에서 업무 훅을 유지한다.

실제 MySQL·Admin→Inquiry 연결에서 다른 대행사·같은 대행사의 다른 광고주 회사 차단, 계정/소속/대상 정책 회수, 읽기·작성 권한 분리, 서명 커서의 필터·계정 바인딩, Unicode 길이·위조 작성자 거절, 동시 메모 재시도 단일 저장과 담당자·상태 버전 충돌을 확인했다. V4→V5 이전에서 기존 문의 버전·행위자 ID와 이름을 보존하고 기존 그룹에 새 권한이 부여되지 않는 것을 확인했다.

실제 Keycloak 대행사·광고주 로그인과 합성 회사의 이메일 초대 수락·게시·공개 문의 접수를 연결해 브라우저로 검증했다. PC 1440px·모바일 390px에서 직원 선택·배정, 내 담당/미배정 필터, 메모 저장·작성자, 기기 전환과 실패 시 초안 보존, 동일 요청 키 재시도, 문의 간 초안 분리, 빈 목록·메모 조회 오류와 재시도를 확인했다. 문서와 모달 안의 가로 넘침은 없었다. 스크린샷은 무시된 `.local/qa/inquiry-*.png`에 보관한다.

## 업무 메뉴별 회사 선택 (2026-11-14)

문의 관리·랜딩페이지·광고주 구성원·광고주 회사 정보를 각각 기본 메뉴에 배치하고 회사 내부 업무 탭을 제거했다. 각 메뉴 오른쪽 회사 목록에서 선택한 한 회사만 표시하며 전체 회사 문의 화면은 제공하지 않는다. 메뉴 진입 시 마지막 회사를 현재 권한으로 재검증하고, 불가하면 해당 업무의 첫 회사를 선택한다. 회사 변경은 현재 업무를 유지하며 대상 회사에 업무 권한이 없을 때 다른 업무로 이동하지 않는다. 문의·랜딩 상세 ID는 다른 회사에서 재사용하지 않고, 회사와 맞지 않는 문의 상세 링크는 안내 오류로 처리한다.

대행사 설정(직원·권한그룹·대행사 정보)과 시스템 설정에는 광고주 회사 선택을 표시하지 않는다. 회사 선택 기억은 issuer·subject·계정 종류·사용자·대행사로 분리한다. 데스크톱은 192px 기본 메뉴와 접을 수 있는 224px 회사 목록, 1100px 미만은 Drawer, 모바일은 BottomSheet를 사용한다. 모바일도 최근/첫 허용 회사로 자동 진입한다. 문의 상담은 회사 목록이 펼쳐진 경우 1440px부터 옆 패널을 사용한다.

회사 선택용 `/client-companies/work` API는 현재 업무 권한과 담당·소속 범위만 조회하며 `client.read`를 추가 요구하지 않는다. JPA/Querydsl로 대행사·허용 회사·이용 중지 조건을 조회한다. 기존 일반 회사 목록 API·문의 API·기존 권한그룹·DB 구조는 유지한다. 기존 Route → 업무 훅 → 기기별 페이지와 공통 UI를 유지했다. 검증 근거는 `.local/qa/work-first-navigation/`에 보관한다.
