# ADR-006: 회사 신청·승인과 이메일 초대

- 상태: 채택·구현
- 일자: 2026-11-12
- 범위: 사용자가 확정한 MVP 화면·회사 등록·검증·초대 설계

## 문제

회사 이름만 만들면 곧바로 업무를 사용할 수 있었고, 계정 ID를 직접 입력해 소속을 연결했다. 사업자 존재 여부, 회사 등록 권한, 대행 관계, 메일 소유권을 구분하는 흐름이 필요했다.

## 결정

회사와 계정의 기존 분리 및 통합 권한그룹을 유지한다. 별도 회사 신청 스냅샷을 만들고 자동 국세청 진위·영업 상태 확인과 운영자의 등록 권한/대행 관계 확인을 모두 통과해야 승인한다. 승인 전 광고주 회사 초안과 랜딩 작성은 허용하되 게시·수집·광고주 이용자 초대는 차단한다. 기존 회사는 자동 승인하지 않는다.

이용자는 인증 서버에서 회원가입하고 이메일을 인증한다. 회사별 이메일 초대는 7일 단일 수락·현재 이메일과 종류 일치·위임 재검사를 적용한다. 회사 검색 가입 요청은 MVP에서 제외한다. 소속은 기존 memberships를 사용하며 초대 수락 후 별도 가입 심사는 없다.

실제 HTTP/SMTP/파일 I/O는 DB 잠금 밖에서 수행한다. 조회 결과는 신청 버전으로, 메일 완료는 임대 세대로 검증한다. nonce+HMAC으로 원문 토큰을 DB에 저장하지 않고 비동기 메일을 재구성한다. 비공개 증빙은 공개 HTML 객체와 분리한다.

## 대안과 영향

- 사업자번호 일치만으로 자동 승인: 등록 권한·계약을 증명하지 못해 제외했다.
- 회사 검색 후 가입 요청: 초대와 이중 흐름이 되어 MVP에서 제외했다.
- 모든 기존 회사를 승인 처리: 근거 없는 상태 이전이므로 제외했다. 운영자 권한 배정과 회사 재검증 절차가 필요하다.
- 별도 메시지 브로커: 현재 규모는 DB 선점·재시도로 구현한다. SMTP 결과가 불명확하면 중복 메일은 가능하지만 이중 소속 부여는 방지한다.

키 미설정·외부 장애는 확인 대기이며 임의로 성공 처리하지 않는다. 실제 운영 SMTP·국세청 키·비밀키·증빙 보관/삭제 정책은 운영자가 구성해야 한다. audit_logs는 사용자 합의대로 추가하지 않는다. 상세 상태·권한·설정과 검증 절차는 [회사 등록 명세](../reference/08-registration.md)에 둔다.
