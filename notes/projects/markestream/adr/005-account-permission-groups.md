# ADR-005: 회사·계정 분리와 공통 권한그룹

- 상태: 채택 및 구현
- 날짜: 2026-11-11
- 근거: 사용자와 합의한 계정·회사 이름, 그룹 통합, 시스템 전체 대행사 범위, 감사 테이블 제외 요청

## 결정

회사 2종과 계정 3종을 분리한다. 그룹과 권한은 공통 테이블에 두며 대상 타입과 소유 대행사로 구분한다. 소속별 그룹 하나, 광고주 담당 배정, 기능별 대상 정책을 사용한다. 기본 직원 그룹은 팀장·마케터, 광고주 그룹은 광고주다. 시스템 계정은 항상 전체 대행사 범위에서 부여된 작업을 수행한다. audit_logs와 지정 대행사 테이블은 만들지 않는다.

## 구현 선택과 근거

권한 조합은 MySQL 읽기 전용 뷰로 한 곳에 정의하고 Admin·Inquiry가 각자 JPA/Querydsl 모델로 읽는다. 현재 공유 MySQL과 두 서비스의 중복 판정 차이를 줄이고 엔티티 공유를 피하기 위한 선택이다. 업무 API마다 독립 SQL이나 메모리 후처리 필터를 늘리지 않는다. 단점은 스키마·뷰 변경 시 두 서비스의 계약 테스트가 필요하다는 것이다.

정책 변경은 분류 행의 배타 잠금, 업무 쓰기는 같은 행의 공유 잠금으로 조율한다. 저빈도 권한 변경을 위해 전역으로 짧게 직렬화하는 비용을 받아들인다. HTTP 호출 전에 트랜잭션을 끝내고 Inquiry에서 다시 검사한다. 그룹·정책 버전과 마지막 관리자의 실제 권한 검사를 함께 적용한다.

계정 인증과 계정 관리 권한은 분리한다. 시스템 계정은 사전 등록만 허용하며 최초 하나는 명시적 issuer/subject로 부트스트랩한다. 새 기능을 기존 그룹에 자동 부여하지 않으면서도 관리할 수 있도록 대행사의 group.delegate_all과 시스템의 system.policy.manage를 부여 권한으로 사용한다. 제한 관리자는 자신이 실행할 수 있는 범위를 넘겨 위임할 수 없다.

## 이전과 검증

V1·V2를 보존하고 V3로 기존 회사·계정·게시·문의 ID와 행위자를 이전한다. 기존 운영자의 전체 범위와 조회자의 읽기 권한을 보존한다. MySQL 8.4.11 데이터 이전 테스트, 실제 OIDC 검증, 두 API·Worker 연결 테스트를 사용한다. 상세 정책과 실제 확인 상태는 [권한 문서](../reference/07-permissions.md)와 [MVP 현황](../reference/06-mvp-status.md)을 따른다.
